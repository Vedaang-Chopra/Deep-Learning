## Problem
Write a scheduler that picks which of 120 tasks gets each of 5,760 rollouts. Goal: maximise final average pass rate on a hidden eval set from a **different task distribution**.

- **Model:** 5 proficiencies in [0,1]. Starting values are hidden and redrawn for grading.
- **Interface:** `choose()` returns a task, `observe(task_id, passed)` gets the result. Scheduler only sees task shapes and pass/fail.
- **Part 1, `Scheduler`:** all tasks are safe.
- **Part 2, `PoisonScheduler`:** runs on banks with and without poison, and isn't told which. Poison tasks apply credit with reversed sign. Simulator rate is 0–40% of tasks, drawn per bank.
- **Limits:** 75 minutes, then a recorded walkthrough. Reasoning counts more than score, and README expects you to skip things and say why.
- **Instant fail:** reading simulator state or hidden files from the scheduler.

## Mechanics that matter
- **Learning needs disagreement:** spread = `k(8-k)/64`. Flat groups (k=0 or 8) teach nothing, so those 8 rollouts are wasted.
- **Target p≈0.5:** expected spread is `0.875·p(1-p)`, about 0.22 credit-weighted before LR. One group then adds about 0.05 total credit, split by shape.
- **Budget is groups, not rollouts:** 5,760 / 8 = 720 groups. Partial groups are near worthless, so close what you open.
- **Best tasks sit well above current skill:** slope is shallow, so p=0.5 on a single-skill task means `demand ≈ prof + 0.49`. With two equal skills, each component needs about 0.71, so gap ≈ 0.34.
- **Feedback lags:** `prof` only updates every 60 rollouts (5 groups), so 96 updates total. Pass rates inside a window share one model state.
- **Tasks saturate:** updates scale by `(1-prof)`, and tasks stop teaching once they get too easy. Hard tasks must be saved for late, and they cap how far skills can go.
- **Scale is hidden:** you see shape, not demand. Pass rates have to reveal both task scale and `prof`, while the same rollouts also train.
- **Weakest skill bottlenecks:** pass probability is a product. Eval tasks differ, so balance all 5 skills rather than farm whatever is easy on train.

## Core design
1. Fit estimates of `prof` and per-task scale from outcomes (the formula is known).
2. Each group, pick the task with the highest expected gain: spread × share, weighted to the weakest skills.
3. Part 2: poison looks normal within one group. The signal is across groups, where a task's pass rate falls after training on it, and also its skills'. Lag and shared skills make attribution hard. Caution also costs score on clean banks, so that trade-off is worth covering in the walkthrough.

**Recommendation:** use a model-based scheduler, with item response theory (IRT) for estimation and a group-level picker that maximises expected learning. Off-the-shelf curriculum bandits fit poorly here: 720 groups across 120 tasks is only 6 pulls per arm, and the tasks drift as the model learns. Your simulator gives you the pass formula and update rule, so you can share evidence across tasks instead.

## Existing algorithms
| Family | How it picks | Fit here |
|---|---|---|
| **Uniform** | Sweeps all tasks evenly | This is your baseline |
| **Pass-rate priority** ([Kimi k1.5, as summarised in Reinforce-Ada](https://arxiv.org/pdf/2505.17652v2)) | Favours tasks with low recent pass rates | **Poor:** low p means flat groups |
| **Band filter** ([Balanced filtering](https://arxiv.org/pdf/2504.03380v2)) | Keeps tasks with p in 0.25–0.75 | **Good:** matches the spread rule, simple |
| **Learning-progress bandit** ([Graves' Exp3.S](https://arxiv.org/pdf/1907.06214), [ACL survey](https://arxiv.org/abs/2003.04664v2)) | Treats tasks as arms, rewards recent progress | **Weak:** too few pulls per arm, noisy reward |
| **Prioritized Level Replay (PLR)** ([PLR](https://proceedings.mlr.press/v139/jiang21b.html)) | Samples by learning potential, plus a staleness bonus | **Partial:** borrow staleness to refresh old estimates |
| **Adaptive rollouts** ([Reinforce-Ada](https://arxiv.org/pdf/2505.17652v2)) | Moves samples between prompts by need | **Partial:** groups persist per task, so you could pause a flat-looking one |
| **Trajectory difficulty** ([CDAS](https://arxiv.org/pdf/2510.04996v3)) | Estimates difficulty over time, not from one snapshot | **Good:** one group of 8 is noisy |
| **IRT / adaptive testing** | Fits ability and difficulty, then picks informative items | **Best:** same logistic form as `gymsim.py` |
| **Thompson sampling** | Samples from the posterior, then acts greedily | **Later:** good exploration, too slow to build first |

**Why IRT fits best:** in the standard logistic model, an item's information is proportional to `p(1-p)`. That's the same term that drives spread here, so the most informative tasks are also the ones that teach most.

## How to build it
1. **Reduce the unknowns.** Since `demand = scale × shape`, each task has one hidden number. Add the 5 starting skills and you have 125 unknowns.
2. **Replay skill changes.** Credit depends only on the observed `k`, so given starting skills you can compute `prof` over time. In Part 1, the unknowns are then fixed numbers, not moving targets. I still need to confirm exactly how banked credit lands in `gymsim.py`.

Then score each task by `(1 - 2q) × gain` and drop it when that goes negative. On clean banks, `q` should stay low, so the cost is limited to false positives. You listed four, so here are all four. Each answers a different question.

## 1. IRT / adaptive testing: "How good is the student, and how hard is each question?"
Think of an online exam like the GRE. If you get a question right, the next one is harder. If you get it wrong, the next one is easier. After a few questions, it knows your level.

IRT (item response theory) is the math behind this. It gives every student an ability score and every question a difficulty score, and predicts the chance of a correct answer from the gap between them. Questions you're 50/50 on tell it the most, because one you'd surely get right or wrong reveals little.

**Here:** the model is the student and tasks are the questions. We use pass/fail results to estimate both skill and task difficulty.

## 2. Thompson sampling: "How do I choose when I'm unsure?"
Say you're choosing between restaurants, and you've only tried each one a few times. You could always go to the current best, but you might miss a better one.

With Thompson sampling, you imagine one plausible version of the world based on what you know, then pick the best option in that version. Next time, you imagine a new version.

- **Little data:** your guesses vary a lot, so you try many options.
- **Lots of data:** your guesses settle, so you stick with what works.

Exploring more or less then happens automatically.

**Here:** rather than always picking the task that looks best, we sample a guess of its difficulty and choose based on that. Tasks we know little about still get tried.

## 3. Trajectory difficulty: "Don't judge a task by one result"
A student scores 40% on one quiz. That could be a bad day. Watch their scores over ten quizzes and you get a much better picture.

This method tracks a task's pass rate over the whole of training, not just its latest number.

**Here:** a group of 8 is noisy. A task with a true 50% pass rate can easily come back 2/8 or 6/8, so one group shouldn't decide a task's fate.

## 4. Adaptive rollouts: "Stop spending where you've already got the answer"
A teacher gives 8 practice problems of one type. If the student gets the first 4 instantly, the other 4 add little, so it's better to move them to a topic where the student is struggling.

Normally, every task gets the same number of attempts. Here, attempts move to where they're most useful.

**Here:** if the first few rollouts of a group all pass or all fail, the group is likely to end flat and teach nothing. We can pause that task and spend the rollouts elsewhere. The catch is that rollouts in a group that never fills are mostly wasted, so pausing isn't free.

## How they fit together
| Technique | Job in our scheduler |
|---|---|
| IRT | Estimates skill and task difficulty |
| Trajectory difficulty | Uses all past results, not just the latest |
| Thompson sampling | Decides when to try uncertain tasks |
| Adaptive rollouts | Pauses groups that look flat |

IRT is the core of the scheduler, and trajectory difficulty comes with it because the fit uses all past results. Thompson sampling and adaptive rollouts are optional add-ons if time allows.

### 1. IRT adaptive testing: "work out the student and the questions together"
IRT (item response theory) gives the student an ability score and each question a difficulty score. The chance of a correct answer depends on the gap between them.

- **Example:** a question that a strong student fails must be hard. A student who solves a hard question must be strong.
- **Adaptive part:** the tutor updates both scores after each answer, then picks the next question near the student's level. This is how computer-based exams like the GRE work.
- **In our problem:** student = the model's 5 skills, question = a task, and we already know the exact formula.

### 2. Thompson sampling: "act on a plausible guess"
The tutor isn't sure how hard the questions are, so they don't rely on a single estimate.

- **Example:** the tutor thinks question 12 is "probably medium, but could be easy or hard". Before each pick, they imagine one possible version of the world that fits what they've seen so far, then choose the best question for that version.
- **Why it helps:** when the tutor is unsure, the imagined versions vary a lot, so they try different questions. As evidence builds up, the guesses settle and they stick with what works.
- **In our problem:** it decides how much to explore unknown tasks versus use known good ones.

### 3. Trajectory difficulty: "judge a question by its history"
One result can mislead. Maybe the student got question 5 right today by luck.

- **Example:** the tutor looks at the full record: wrong in week 1, half right in week 2, always right in week 4. That shows how hard the question really was and how the student grew past it.
- **In our problem:** one group of 8 rollouts is noisy, so we estimate difficulty from all the groups on a task over time.

### 4. Adaptive rollouts: "don't spend the same effort on every question"
Normally the student attempts every question the same number of times. Here, the tutor adjusts as the results come in.

- **Example:** the student gets a question right 4 times in a row, so it's probably too easy. The tutor stops there and moves those remaining attempts to a question with mixed results.
- **In our problem:** the first few rollouts in a group can hint that it will come back flat, so we could pause that task and save budget. The catch is that an unfinished group teaches very little, so stopping too often wastes rollouts.

### How they fit together
| Technique | Question it answers |
|---|---|
| IRT | How strong is the student, and how hard is each question? |
| Trajectory difficulty | Which evidence should those estimates use? All of it, not just the latest result |
| Thompson sampling | Which question next, given what's still unknown? |
| Adaptive rollouts | How many attempts should this question get? |

## Weak spots
- **Skill collapse at heavy poison:** at 40%, one bank still scores 0.519. Its true coding skill fell to -0.81 while rollouts on poison coding tasks were about double those on clean ones (792 vs 384). It looks like a skill with mostly poison tasks can spiral, because damage grows as skill falls.
- **The clamp fix didn't solve that:** removing the lower limit corrected the estimator but barely changed scores. A likely next idea is a per-skill alarm that stops training a skill when its tasks all get harder, but I haven't tried it.
- **Low budgets:** at 960 rollouts there's too little evidence to spot poison, and it lost 3 of 10 banks to the baseline, by up to 0.0655 on the worst one.
