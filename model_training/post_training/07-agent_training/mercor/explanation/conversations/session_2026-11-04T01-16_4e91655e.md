# Write Notebook

A notebook is not a wrapper around `interfaces.py`. A notebook is a structured testing, debugging, and understanding surface for one feature, module, or workflow.

A human running the notebook should be able to answer:

* What feature is being tested?
* What inputs does it consume?
* What intermediate states are created?
* What outputs are produced?
* What assertions prove it is working?
* What edge cases fail or behave differently?
* What artifacts, files, logs, or visuals are created?
* How does this feature fit into the larger module?

---

## Trigger

Use this skill when:

* Creating a new Jupyter notebook for a feature, module, or workflow.
* Updating an existing notebook after a feature change.
* A notebook only calls one function from `interfaces.py`, `api.py`, or `runners.py`.
* Building a notebook-based validation artifact for a technical spec.
* Any AI/ML pipeline, data processing, evaluation, visualization, or agentic workflow needs notebook-based inspection.

---

## Output Location

`notebooks/<module_or_feature_name>_inspection.ipynb`

---

## Before Creating the Notebook

Write this plan first. Do not create the notebook until it is written.

```markdown
## Notebook Plan

### Notebook path
`notebooks/<feature_name>_inspection.ipynb`

### Feature being tested
Short description.

### Public entry points used
- `module.interfaces.run_feature`
- `module.runners.run_stage_a`

### Sections
1. Purpose
2. Setup
3. Test Inputs
4. Public Entry Point Check
5. Stage-by-Stage Inspection
6. Assertions
7. Edge Cases
8. Artifact Inspection
9. Debugging Notes
10. Summary

### Expected assertions
- Assertion 1
- Assertion 2

### Expected artifacts / outputs
- Output 1
- Output 2

### What this notebook will NOT test
- Exclusion 1
- Exclusion 2
```

## Required Notebook Structure

```markdown
# <Feature / Module Name> Inspection Notebook

## 1. Purpose
What feature or module is this notebook testing?
What should a human understand after running it?

## 2. Setup
Imports, config loading, path setup, logging setup.
No feature logic here.

## 3. Test Inputs
Load or construct small representative inputs.
Show input summaries, shapes, keys, paths, or sample records.

## 4. Public Entry Point Check
Import and call the public entry point from `interfaces.py`, `api.py`, or `runners.py`.
Show the top-level output.

## 5. Stage-by-Stage Inspection
Run smaller production stage functions if available.
For each stage:
- call the production function
- display intermediate output
- check type / shape / schema
- explain what changed

## 6. Assertions / Expected Behavior
Add lightweight notebook assertions:
- output type
- required fields
- shape / count checks
- artifact existence
- schema validation
- metric thresholds if applicable

## 7. Edge Cases / Failure Cases
Run at least one malformed, missing, empty, or unusual input case.
Show the error or fallback behavior.
Do not hide failures.

## 8. Artifact / Output Inspection
Inspect files, plots, logs, generated outputs, saved data, or visualizations
created by the feature.

## 9. Debugging Notes
Explain what to check if this feature fails.
Point to relevant modules, logs, configs, and docs.

## 10. Summary
Short summary of what passed, what failed, and what was not tested.
```

For agentic / LLM systems, the stage order should follow:
```
input → prompt construction → model call → parsing → validation → downstream behavior → artifacts
```

For ML / data systems:
```
data load → preprocessing → model / input construction → inference step → metrics → visualization
```

## Rules

### 1. Notebooks test behavior — they do not just call wrappers

A notebook must inspect the feature's behavior across multiple cells and stages.

Do not create notebooks that only do this:

```python
from module.interfaces import run_feature
result = run_feature(...)
result
```

### 2. Notebooks call production code — they do not reimplement it

**Allowed in notebook cells:**

* setting parameters
* constructing small test inputs
* calling production functions
* displaying intermediate outputs
* simple assertions
* visualizations
* debugging printouts
* summaries

**Not allowed in notebook cells:**

* core algorithms
* schema definitions
* parsing logic
* retry logic
* model / provider setup logic
* reusable data transformations
* reusable evaluation logic

If a cell grows into a reusable function, move it into a Python module immediately.

### 3. Use public entry points; expose stage functions where needed

Start from the public entry point (`interfaces.py`, `api.py`, or `runners.py`).

For stage-by-stage inspection, those stage functions must be exposed through the public interface — do not import random deep internal files to make a notebook work.

If needed, update the public interface to expose stable, inspectable stage-level functions.

### 4. One notebook per feature / workflow

Do not create one giant notebook covering the whole codebase.

A notebook should correspond to one feature, one module, one workflow, one technical spec, or one debugging path.

### 5. Assertions are required

Every notebook must include lightweight validation.

```python
assert result is not None
assert isinstance(result, ExpectedType)
assert "required_field" in result
assert output_path.exists()
assert len(records) > 0
```

These are not a replacement for unit tests. They make notebooks executable inspection artifacts.

### 6. Edge cases are required when meaningful

Include at least one edge or failure case unless the feature is purely visual or exploratory.

Examples: empty input, missing file, malformed schema, invalid config, failed model output, no records found, bad path, unsupported option.

### 7. Artifacts must be inspectable

If the feature creates files or outputs, the notebook must show:

* where artifacts are written
* what files were created
* what their basic contents or shape look like
* how to verify them manually

### 8. Cells run top-to-bottom with no hidden state

Notebook cells must run sequentially from top to bottom. Do not rely on state from previous manual experimentation.

### 9. Clear outputs before committing if the repo policy requires it

If the repo rule says clear outputs, clear them before commit. If the notebook is meant to be a saved report, state that explicitly in the spec.
