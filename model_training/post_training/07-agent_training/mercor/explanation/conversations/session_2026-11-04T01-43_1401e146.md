**Setup, as a school**

- The model is a **student**.
- It has **5 skills**, like Math, Reading and Science.
- The task bank is a **homework pile** of 120 problems.
- You get a limited number of **practice sessions** (rollouts).
- Each session you pick problems. The student attempts each one several times (a "group"). Afterward the student improves a bit.
- At the end, an exam (eval) measures how good the student got.

**Why picking matters (the GRPO rule)**

The student only learns from a problem if their attempts *differ*:
- Too easy: all attempts right. Nothing to learn, so the signal is zero.
- Too hard: all attempts wrong. Nothing to learn, so the signal is zero.
- Just right: some right, some wrong. Strong learning.

So a good teacher assigns problems at the edge of what the student can do. The baseline scheduler picks blindly and wastes sessions on too-easy or too-hard problems.

**How the scheduler works (3 parts)**

1. **Track the student (`SkillTracker`).** Keep a guess of the student's level in each of the 5 skills. Everyone starts at a fixed guess of 0.30. After each session, update the guesses from how attempts went.

2. **Track each problem (`TaskModel`).** Keep a guess of how hard each problem is. The guess starts vague. Each time the problem is attempted, the guess sharpens. This is the "Bayesian" part. It is like a teacher noticing that nobody solves Q47 and concluding it's really hard.

3. **Pick the best problems.** For each problem, ask: "Given this student's current level in that skill, will attempts be mixed?" Prefer problems where the odds are near 50/50. Also give extra weight to skills with the most room to grow ("headroom"). If Math is at 0.9 and Reading is at 0.3, practice more Reading.

This follows the IRT idea (matching problem difficulty to student ability), as in adaptive tests like the GRE.

**Setup:** A tutor has 720 practice sessions. Each session is 8 attempts at one problem. The tutor decides which problem to use for each session.

**Step 1: Rate every problem before choosing.**
Each problem gets a score from two questions:

If two problems tie, the earlier one in the list wins. No randomness, so the same run always gives the same result.

**Step 3: Stick with it for 8 attempts.**
The tutor doesn't switch problems mid-session. One session means 8 attempts on one problem.

After the 8 attempts, the tutor notes two things:
- How the problem went. If 4 of 8 passed, it's about the right difficulty. If 0 passed, it's too hard for now.
- How much the student probably improved. This is saved up, not applied yet.

**Step 5: Every 60 attempts, update the student's report card.**
The saved-up improvement is added to the tutor's estimate of the student's skills. Then every problem is re-scored, because the student has changed. A problem that was too hard may now be a good fit.

- The baseline tutor hands out problems in list order, 8 attempts each, and never adapts. Many of those sessions are wasted on problems that are too easy or too hard.

**What a candidate difficulty means**

For a given student skill and a given candidate scale, you can work out the pass chance. I'll use one skill and a skill estimate of 0.30. The numbers below are my hand calculation from the formula in `pass_probability`, so they're approximate.

| If the problem's scale were... | Pass chance per attempt |
|---|---|
| 0.1 (easy) | about 98% |
| 0.3 | about 95% |
| 0.5 | about 85% |
| 0.8 | about 49% |
| 1.2 (hard) | about 8% |

When scale equals skill, the pass chance is 95%. That's the README's "OK" level.

**Update: the group comes back 4 of 8**

Now ask, for each candidate: "if this were the true difficulty, how likely is *4 passes out of 8*?"

| Candidate scale | Chance of seeing 4 of 8 |
|---|---|
| 0.1 | almost none |
| 0.3 | almost none |
| 0.5 | tiny |
| **0.8** | **by far the highest** |
| 1.2 | very small |

Rescaled so they add to 1, the odds become roughly: scale 0.8 at about 93%, scale 0.5 at about 6%, and the rest near 0. (This uses only those five candidates, so it's an illustration, not the exact output.)

So the tutor now believes this problem sits around scale 0.8. It's not certain, but it's a lot less vague. This update is `observe_group`.

**Using the belief: `expected_spread`**

To score a problem, the tutor asks: "at the student's current skill, how mixed will the next group be?" It computes `p × (1−p)` for every candidate scale, then averages those, weighted by the probabilities. If the belief is mostly "scale 0.8" and the pass chance there is about 49%, the spread is high, so this problem scores well.

**Why the belief stays alive**

The code notes: "A task that fails now stays alive." If the student fails 0 of 8, the belief moves to "hard". But the pass chance is always computed from the student's *current* skill, so as skill grows the same belief gives a better pass chance, and the problem scores well again later.

Not random. Every candidate starts with the same probability.

From `TaskModel.__init__` in `curriculum/skill_model.py`:

```python
self.weights = [1.0 / len(self.GRID)] * len(self.GRID)
```

- The grid has 52 candidate scales: 0.05, 0.10, ... up to 2.6.
- Each gets a probability of 1/52, about 1.9%.
- All 120 tasks start with the same flat belief. Nothing random is involved. It's a "don't know" starting point.

**Two different "hidden numbers"**
- **The real scale** of each task is hidden in the simulator. It is drawn from the run's salt (`difficulty_salt: "practice-bank-v2"` in `config/run.json`) and redrawn for grading. That one is random, but the scheduler never sees it.
- **The scheduler's belief** about each scale is the flat list of 52 equal probabilities. That one is fixed and deterministic.

So the scheduler starts with no preference and learns each task's scale from the pass/fail results alone. The seed isn't used in the scheduler either, as the `Scheduler` docstring notes: "The seed is unused because picks are deterministic: ties resolve by bank order."

A caveat on the 52 count: 2.6 / 0.05 is 52, and the code builds the grid with `range(1, int(MAX_SCALE / SCALE_STEP) + 1)`. Floating-point rounding could make that 51 or 52. I haven't run it to confirm, so treat 52 as approximate.
